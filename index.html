Dual-Arm Robotic Rubik's Cube Solver

A camera, Kociemba's two-phase solver, a MuJoCo model of the rig, and two stepper-driven grippers that can only reach two of the cube's six faces.

Real robot · 4×

The robot holds a scrambled cube corner-down between two grippers, rolls it through five poses so an overhead camera can see every face, solves the state with Kociemba's two-phase algorithm, and then turns the layers itself. Each gripper can turn only the layer behind the edge it clamps, so most moves start by rolling the whole cube to bring the right layer into reach. A MuJoCo model of the rig runs the same controller and decides every roll, clamp and turn before the motors move.

The mechanism

With the grippers fixed to the frame, only two of the six layers are within reach at any time. The controller keeps a 3×3 integer matrix from the machine frame to the cube's own frame and updates it after every roll. For each requested move it searches breadth-first over sequences of single-gripper rolls for the shortest one that brings the target layer into a gripper's slot, picking whichever arm needs fewer rolls. Half turns run as two quarter turns, because the wrist only travels ±90°.

  1. ParseRead the next Singmaster token, e.g. R'.
  2. MapConvert it to an axis, a layer and a direction in the cube's frame.
  3. Choose an armThe one whose slot needs fewer rolls to reach that layer.
  4. Roll if neededOne gripper holds and turns; the other opens, then re-clamps.
  5. Turn the layerBoth grippers hold; the active wrist turns 90°.
  6. ResetRelease the active gripper, return its wrist to neutral, clamp both again.

Primitive packets

The interface between the planner and the rig is deliberately small: an ordered list of four kinds of command. The simulation never streams poses or trajectories; whatever the controller decides is written down as these packets, and the same list drives the real motors.

OpFieldsWhat the rig does
CLAMPsideClose one gripper.
RELEASEsideOpen one gripper. Refused unless the other gripper is closed, so the cube is never dropped.
DUAL_HOLDnoneBoth grippers closed; the safe resting state between moves.
ROTATEside, angleDrive one wrist to −90°, 0° or +90°. With the other gripper open this rolls the cube; with both closed it turns a layer.

On the wire, the host sends each packet as one line of JSON carrying both grippers' target state, and blocks until the Arduino answers DONE:

{"L":{"state":1,"angle":1.5708,"action":"ROTATE"},
 "R":{"state":0,"angle":0.0,"action":"HOLD"},
 "t_ms":400}                       // → "DONE"

Two additions came from running the real rig. Stepper clamps slowly lose grip under load, so after each return to a dual hold the bridge sends a short RECLAMP that presses both jaws inward again. And after a release leaves the cube in one gripper, it waits 300 ms while the holding side keeps creeping inward before the next rotation starts.

Reading the cube

The camera's auto-exposure and auto-white-balance are switched off at start-up, so colours don't shift when the white arms move through the frame. The scan rolls the cube through five poses, each showing two faces; the ten face views are sorted by position into rows and columns and fused into the 6×3×3 state the solver needs.

    The cube ended solved in all 1000 runs, so the controller's orientation tracking and roll planning hold up on arbitrary states. Rolls are the cost of fixed grippers: a median solve adds 23 of them to 30 quarter turns, and each roll is a release, a one-handed rotation and a re-clamp. That, not the 14 ms the solver takes, is where the real rig's two minutes per solve go.

    What we'd fix next

    Closed-loop motors. The steppers run open-loop. A lost step is invisible to the software, and from then on its idea of the cube no longer matches the real one; encoders, or a quick re-scan after each move, would catch it.

    Contact. The simulation assumes each jaw lands on the centre of an edge piece. On the rig, a few millimetres of misalignment can turn the wrong layer, and the printed jaw faces rely on clamping force; grippier pads would tolerate more error.

    Speed. Every packet waits for the previous one to finish. Starting the next clamp while a rotation settles, and choosing rolls that also shorten later moves, would cut most of the idle time.

    Lighting. The colour classifier was trained under one lighting setup and hasn't been tested under others.

    Side work: a servo-control board

    Zhuoyang also designed a two-layer servo-control board: a PCA9685 16-channel PWM driver on I²C, an XL4015 buck stage for a 5 V servo rail, an AMS1117 3.3 V logic rail, a fused and diode-protected input, and separate servo and logic grounds. Both rails and all 16 PWM channels were verified on the bench.

    The final rig switched to stepper motors driven from an Arduino Nano Every, so this board is not part of the system shown above.
